# Negotiation Ground-Truth Generator (gtgen)

Builds a benchmark of **turn-based, persona-driven procurement negotiations** grounded in real GeM
buyer constraints and IndiaMART candidate products/suppliers. Output is ground truth (GT) for a
**probabilistic recommendation / ranking system**: every conversation ends with a ranking matrix,
reference labels, and full provenance.

Authoritative inputs (read before any data or schema work):
- `docs/canonical_data_analysis_guide.md` — retained columns, join keys, file roles. **Binding.**
- `docs/Procurement_Negotiation_Benchmark_Research.docx` — research framing, PASS/FAIL/UNKNOWN, GT label types.

> Terminology. "Subagents" = Claude Code development helpers in `.claude/agents/`.
> "Runtime agents" = the Buyer simulator and Negotiator inside the application (`src/gtgen/dialogue/`).
> Never confuse the two. Defining a subagent file implements nothing in the application.

## 1. Non-negotiable domain rules

1. **`golden_param` is the hard/soft determinant.** Never rename, drop, infer, or overwrite it.
   Mapping (configurable, `config/settings.yaml: golden_param_true_means`): `True` → HARD, `False` → SOFT.
   Confirmed by the user (2026-10-26).
2. **Canonical columns only.** Loaders select exactly the retained headers in section 4 of the
   canonical guide. Join keys: `gem_bids_metadata.bid_number` ↔ `final_constraints.bid_id` ↔
   `products.gem_bid_id`; `product_id`; `supplier_id`. Names are never join keys. Newer exports
   may explode a retained JSON column into `<column>.<key>` headers (and carry the constraint list
   under `constraints`); the loader reconstructs the canonical JSON-object column, so downstream
   contracts see the same schema for both layouts.
3. **Retrieval ≠ compliance.** `relevance_score` / bid association means "candidate", never "satisfies".
4. **Commercial framing.** Data comes from government bids, but every buyer is a fictional
   **private or commercial company**. No GeM, bid numbers, ministries, EMD/ePBG, MSE/MII preferences,
   or tender language may appear in any utterance. Government-only constraints are dropped or
   translated to a commercial equivalent by the reframing step, and the decision is recorded.
5. **Information barrier.** The Negotiator sees **only** (a) the conversation transcript
   (`TranscriptView`) and (b) the IndiaMART catalogue view (`CatalogueView`). It never sees
   `final_constraints.csv`, `gem_bids_metadata.csv`, `golden_param`, persona parameters, or
   bid-derived product fields (`gem_bid_id`, `product_target`, `search_keyword`,
   `relevance_score`). Enforced by types and tests.
6. **Hard constraints are never relaxed.** The Negotiator may *propose* anything it believes is soft
   (it infers softness from the buyer's wording); the Buyer policy always answers NO to a HARD
   relaxation. UNKNOWN on a HARD constraint is never treated as PASS. By design (D048, amended 2026-10-29) a HARD *or SOFT* constraint (never a synthetic commercial term) whose evidence
   coverage in the bid pool is below `scenario.negotiated_min_coverage` has `scenario_role = verification_only`: the buyer
   still voices it and it is listed in `verification_required` for every recommended candidate. Only MISSING evidence is
   unscored (it neither blocks nor passes anyone); an OBSERVED FAIL (real contradicting evidence) is a violation and still
   counts (`scenario.verification_only_fail_blocks`). Also (D069): a HARD or SOFT (non-synthetic) constraint that no candidate in the full pool PASSes (0 PASS) is `verification_only` with `role_reason = zero_pass` (>= 1 PASS keeps it negotiated). Every `negotiated` constraint keeps the full rule.
7. **Compliance statuses (four):** `PASS`, `FAIL`, `UNKNOWN`, `PENDING_VERIFICATION`.
   `PENDING_VERIFICATION` = the supplier/product evidence *claims* the attribute (e.g. "ISO 9001
   certified") but proof is a document not yet seen. It **does not lower** rank or score; the doc is
   added to the candidate's `pending_verification_docs` list. `UNKNOWN` = no evidence either way.
   A claim is detected by an LLM that must quote the listing; code verifies the quote occurs in the listing text, and an
   unverified quote is no claim (D051). A SOFT doc-proof constraint with no claim blocks (FAIL, evidence `no_claim`) and may
   be relaxed through `doc_to_pending` (buyer answers BYPASS); a HARD doc-proof cell with no claim is `verification_only`.
8. **Unsupported claims are bugs.** No utterance may assert a supplier/product fact absent from the
   catalogue evidence.
9. No claims of runs, files, or passing tests unless they actually happened in this session.

## 2. LLM vs deterministic split

"Generated by an LLM wherever applicable" (user requirement) is implemented as:

| LLM (Gemma 4 via OpenRouter) | Deterministic code (reproducible GT labels) |
|---|---|
| Commercial reframing of bid constraints (keep / translate / drop + reason) | CSV loading, canonical filtering, joins |
| Buyer company profile + persona JSON incl. the random hardness threshold τ and preference weights | Tier binning of τ, accept/reject/counter arithmetic |
| Buyer and Negotiator utterances (natural, in-persona) | Compliance comparison of normalised values |
| Attribute alignment (buyer attribute ↔ product spec names), per bid, cached | Relaxation search and candidate-gain counting |
| Free-text value normalisation (brochure/description → value+unit) | Ranking matrix, probabilities, metrics |
| Verification-document classification (is this constraint "prove-by-document"?) | State transitions and GT record assembly |
| Negotiator's extraction of buyer constraints from the transcript | |

Rationale: LLMs provide semantics and variety; arithmetic labels must be reproducible and auditable.
Every LLM output is schema-validated, cached, and referenced by `llm_call_id` in the GT record.

### LLM client rules
- Model: `google/gemma-4-26b-a4b-it:free` (D022) on OpenRouter (`OPENROUTER_API_KEY`), Google AI Studio key added
  as BYOK in OpenRouter; provider pinned in `config/settings.yaml`. Confirm the provider slug in the
  OpenRouter dashboard.
- API keys are per role (`llm.api_key_roles`, D063) and may be pooled (`llm.api_key_pools`, D084/D086). A pooled role
  round-robins over its usable accounts and each account keeps its own limiter; `claims`, `buyer`, and `negotiator`
  pool all five accounts because the claims batches and the dialogue calls are otherwise paced by one key. Live pilots
  run one bid per process (`scripts/live_all_bids.sh`), never all bids in one process.
- The pilot creates `out/gt/<run_id>/` before the first LLM call and appends each finished conversation to
  `conversations.jsonl` (plus skipped rows to `skipped.jsonl`) with an fsync, so a timeout/crash keeps every completed
  bid/persona (D086).
- Max ~8k completion tokens → batch small (≤ 25 constraints per call).
- Structured output via `response_format: json_schema`; validate with the pydantic model; on failure retry
  `llm.max_retries` times carrying only the most recent rejected answer + the validation error (so the prompt
  cannot grow past `llm.max_tokens_per_call`); then raise `ScenarioSkipped` (D066), never guess. A budget error
  (`LLMBudgetError`) is also a `ScenarioSkipped` (skip the bid), never a run-aborting error.
- Cache key = sha256(model, backend, provider, prompt_name, prompt_version, canonical-JSON inputs, seed) = `llm_call_id` (D018). Cache in
  `.cache/llm/`. Re-runs must be byte-identical when the cache is warm.
- `GTGEN_LLM_MODE=mock` for tests: no network, fixtures from `tests/fixtures/llm/`.
- Prompts live in `prompts/<name>.v<N>.md` with a header listing input vars and output schema name.
  Changing a prompt bumps the version.

## 3. Ground-truth generation algorithm (reference)

Per scenario = (bid, persona_seed):
1. **Reframe** bid constraints into a private-company buyer brief (LLM). Record per-constraint
   `framing_decision`.
   **Scenario construction (D046, D048, D049):** merge clause-conformity members that have no measurable value into one
   doc-proof constraint per standard and hardness (`framing_decision = merge`, `merged_from`); give every constraint a
   `scenario_role` (negotiated / verification_only / dropped) and an `evidence_coverage`; add the simulator-defined SOFT
   commercial terms (`provenance = synthetic_commercial`, `golden_param = None`) with values the persona LLM picks inside
   code-derived bands, under a per-scenario tightness target. Target, actual initial count and tightening steps are
   recorded in `ScenarioBrief.scenario_meta`.
   **Supplier rating and years of experience are never constraints and never spoken (D070)**: they are ranking-only features;
   supplier priority is location (voiced as preferred states) > years of experience (cold start) > rating, enforced in the weights.
2. **Persona** (LLM, temperature ≥ 1.0, nonce = scenario seed): two outputs —
   `BuyerProfile` (company name, industry, city, speaking style) and `Persona` (hardness τ ∈ [0,1],
   per-category tolerance multipliers, counter band, patience turns, ranking weights).
   Tier by τ: `<0.25 lenient`, `<0.50 medium`, `<0.75 medium_strict`, else `strict`.
   QA checks that τ across scenarios is spread (LLMs are poor random generators).
3. **Opening**: Buyer LLM writes the request from the `ScenarioBrief` (which includes quantity,
   budget, and constraints). GT records which constraint IDs were revealed (explicitly verified
   by a post-hoc LLM check, not assumed).
4. **Negotiator turn** (barrier-enforced): receives `TranscriptView` + `CatalogueView` only.
   Extract believed constraints from transcript (via `AttributeAlignment` + `NormalisedValue` LLM
   calls) → validate all candidates → if feasible count ≥ `min_shortlist`, recommend; else run
   **relaxation search**: for each believed-soft constraint, compute candidates gained at each
   relaxation step (numeric: distinct candidate values; categorical: candidate value alternatives;
   doc-type: convert to pending verification), rank by gain, tie-break by smallest normalised
   relaxation cost. **Bundle proposal** (D025): near-miss search — candidates infeasible only because
   of ≤ `max_bundle_size` SOFT FAILs; enumerate subsets of those soft blockers (≤ 4 items), each item
   relaxed to the level the near-miss candidates need; keep **minimal** bundles (removing any item
   lowers joint gain by ≥ `min_marginal_gain`); rank by joint gain desc → fewer items → lower total
   normalised cost → stable key. Propose the top bundle in a single turn, phrased by a
   sales-motivated but truthful Negotiator LLM. Numeric `=` (D026): with `allows_higher` treat as
   `>=`; otherwise relax to a symmetric band around the target.
   May also counter a buyer counter-offer with the nearest value that yields ≥ 1 additional
   candidate.
5. **Buyer turn** — action decided by the deterministic policy, per item in the bundle:
   - HARD constraint → `NO`.
   - Doc-proof constraint where supplier claims the attribute → `BYPASS` (candidate stays, doc listed
     with `doc_name`).
   - Normalised cost r ≤ a, where a = (1−τ)·w_category → `YES`.
   - r > tol and it.current_level ≤ tol < r → `COUNTER` at tolerance level (every tier); otherwise `NO`.
   - Otherwise `NO`.
   When a bundle has mixed responses, the buyer's turn-level action is `MIXED` and
   `proposal_outcome` is `PARTIAL`; `item_responses: list[ItemResponse]` records each item's
   individual action. The total number of YES + BYPASS responses in a turn is capped by
   `persona.max_concessions_per_turn`. The Buyer LLM verbalises the decided actions in persona
   style. Each turn records `proposal_outcome` ∈ {ACCEPTED, REJECTED, COUNTERED, BYPASSED,
   PARTIAL} and, for a COUNTER, `counter_value`.
6. Loop until shortlist reached, patience exhausted, or no relaxable options remain. The negotiator ALWAYS recommends
   something (D050): when nothing satisfies every negotiated constraint, or patience runs out, it recommends the best
   available candidates (`BEST_AVAILABLE`).
7. **Final**: outcome ∈ {`RECOMMENDED`, `BEST_AVAILABLE`} (`NO_FEASIBLE_OUTCOME` and `PATIENCE_EXHAUSTED` are removed, D050;
   `best_available_reason` keeps no_feasible / patience_exhausted / nothing_verified (D075: feasible only on unscored beliefs)). `BEST_AVAILABLE` holds the top-k candidates by
   `match_original` with `unmet_constraints` and `verification_required`; a candidate with a negotiated HARD FAIL may appear only
   with `non_compliant = true` and counts in the hard-violation metrics. `match_original` (stored per `RankingRow`, and
   `top1_match_original` per conversation) = weighted share of the ORIGINAL negotiated constraints the candidate satisfies
   (HARD weight 2, SOFT weight 1, verification_only excluded). A *perfect deal* = the top-1 recommendation satisfies every
   negotiated constraint in the final agreed truth state. Per-tier targets live in `recommendation.tier_targets`; scenarios are
   calibrated deterministically (no LLM) by simulating the negotiation for each tightness candidate; one that cannot be
   calibrated keeps the qa_flag `uncalibrated`. Two ranking
   matrices: `reference_ranking` (from the FINAL agreed buyer truth state, D052; `reference_ranking_initial` is the
   truth ranking before any concession) and `negotiator_ranking` (from belief state). Aggregated `pending_verification_docs` and per-candidate per-constraint
   `compliance_detail_truth` / `compliance_detail_belief` for auditability.

### Ranking matrix (one row per candidate) and probability
Columns: `product_id, supplier_id, hard_pass, hard_fail, hard_unknown, soft_pass, soft_fail,
soft_unknown, pending_verification_docs, spec_match, price_score, price_vs_budget, moq_fit,
rating_bayes, rating_count, tenure_years, location_match, evidence_confidence, p_feasible, utility,
score, p_recommend, rank`.
- `p_feasible = Π p_c`: PASS → evidence confidence (×0.9 if `raw_text_verified` false);
  PENDING_VERIFICATION → same as PASS (no penalty, rule 7); SOFT UNKNOWN → 0.5; SOFT FAIL → 0.3;
  HARD UNKNOWN or HARD FAIL → 0 (excluded from shortlist, kept in matrix).
  `verification_only` cells (D048, `ComplianceCell.scored = False`) are not part of the product and not counted in
  the `hard_*` columns; their attributes go to `verification_required`.
- `utility = Σ w_i · feature_i` with weights from the persona (normalised to sum 1).
- `score = p_feasible · utility`; `p_recommend = softmax(score / T)`; ranking = Plackett–Luce
  expected order (equals sort by score). Constants live in `config/settings.yaml`.

### Evaluation metrics module must provide
NDCG@k, MRR, Precision@k, Recall@k, MAP, Kendall τ (vs reference ranking); Brier score and ECE for
`p_feasible`; false-feasibility rate; hard-violation rate among recommended; catalogue coverage;
negotiation: policy-compliance rate, state-transition accuracy, candidates gained per relaxation,
turns to agreement, BEST_AVAILABLE share; per-tier perfect-deal share, match% distribution and share of conversations in
band (D050); barrier-leak count; unsupported-claim rate.

## 4. GT output (JSONL, one conversation per line) — schema in `src/gtgen/contracts.py`
`GTConversation`: scenario_id, run_id, bid_ref (hidden), buyer_profile (`BuyerProfile`),
persona (`Persona`), commercial_brief (`ScenarioBrief`: scenario_id, bid_ref, quantity,
quantity_unit, budget_inr, constraints[]),
turns[] (turn_idx, speaker, action, utterance, proposal, proposal_outcome, counter_value,
item_responses[], revealed_constraint_ids, buyer_truth_state_after, negotiator_belief_state,
feasible_count_truth, feasible_count_belief, llm_call_ids),
final (`FinalOutcome`: outcome ∈ {RECOMMENDED, BEST_AVAILABLE}, best_available, best_available_reason,
reference_ranking[], reference_ranking_initial[], negotiator_ranking[], accepted_relaxations[],
pending_verification_docs[], compliance_detail_truth[], compliance_detail_belief[]),
provenance, qa_flags. Output path: `out/gt/<run_id>/conversations.jsonl`.

A subagent that needs a change outside its paths **stops and reports the needed change** to the
coordinator; it does not edit. Contract changes go through the coordinator and are announced to
every affected owner in their next task prompt.

## 6. Delegation rules for the main session

- Main session coordinates: decompose, write/approve contracts, delegate, integrate, run the
  pipeline, decide conflicts. Subagents do not share context — every delegation prompt must carry
  the task, relevant contract names, file paths, acceptance criteria, and known constraints.
- Order: contracts → (data-steward ‖ llm-engineer client) → (matching-engineer ‖ llm-engineer
  prompts) → dialogue-engineer → gt-auditor → pilot (1 bid × 3 personas) → scale.
- Parallelise only tasks with disjoint owned paths and a frozen contract.
- After every integration: `pytest -q` and `python -m gtgen.cli pilot --mock`; then gt-auditor.
- Conflicting findings: the coordinator re-checks against data/code itself; data and tests beat
  opinions; record the decision in `docs/decisions.md`.
- Add a new subagent only when a new area of work recurs and fits no owner (e.g. a human-annotation
  UI). Do not add agents for one-off tasks.

## 7. Conventions
Python 3.11+, pydantic v2, pandas, pytest. Typed public functions. No network in tests.
Seeds everywhere (`numpy.random.default_rng(seed)`); seed stored in GT. Raw CSVs in `data/raw/`
(git-ignored); canonical parquet in `data/canonical/`. `gst_number` never leaves `src/gtgen/data/`.
